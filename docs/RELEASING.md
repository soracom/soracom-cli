# Releasing

This document describes how maintainers release a new version of soracom-cli.

To release, you need write access to soracom/soracom-cli and soracom/homebrew-soracom-cli, and permission to publish Lambda layers in the AWS account that hosts the public layers.

## Distribution channels

| Channel | What to do on release |
|---|---|
| GitHub Releases | Push a tag, then promote the pre-release that is created |
| `install.sh` | Nothing (it always fetches the latest release) |
| Homebrew (soracom/homebrew-soracom-cli) | Open a PR to update the formula |
| AWS Lambda Layers | Publish the layers to each region |
| Snap | Nothing (deprecated; see [Snap](#snap)) |

## Required tools

- Docker
- [GitHub CLI](https://cli.github.com/) (`gh`)
- AWS CLI, `jq`, `curl`, `zip`

## 1. Decide the version

Review the changes since the previous release and choose a version number according to [Semantic Versioning](https://semver.org/).

```bash
git log --oneline --no-merges v<previous version>..origin/master
```

## 2. Update the API definitions (if needed)

To import the latest API definitions, copy them into `generators/assets/` with `scripts/copy-apidef-files.sh`, then open a PR that includes the code generated by the build (step 3).
## 3. Build and test

On the latest master, build and run the tests by following [How to build in a local environment](../README.md#how-to-build-in-a-local-environment-linux--mac-os-x) in the README. The files built here are for testing only. The files to release are built by GitHub Actions (step 4).

The build regenerates the source code. After the build, make sure that `git status` shows no changes. If any change is left, the release build fails. If it shows changes, open a PR with them, merge it, and build again.

## 4. Push the tag

Tag the commit you tested with a tag in the form of `v<version>` and push it.

```bash
VERSION=1.2.3
git tag v$VERSION
git push origin v$VERSION
```

When the tag is pushed, the Release workflow of GitHub Actions (`.github/workflows/release.yml`) does the following:

1. Builds the files to release
2. Generates a [build provenance attestation](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations) for the built files
3. Generates the release notes and creates a GitHub release as a pre-release

Find the workflow run and wait for it to finish.

```bash
gh run list --workflow release.yml --branch v$VERSION
gh run watch <run ID>
```

> [!WARNING]
> Do not create the GitHub release manually or upload files built locally. The workflow fails if a release for the same tag already exists, and replaced files no longer match their attestations.

## 5. Promote the pre-release

The release created by the workflow is a pre-release. Until you promote it, `install.sh` keeps installing the previous version.

The generated release notes list only PR titles. Add the main changes and any behavior changes. Changes merged into master have already been reviewed in their PRs, so the release does not need a review by another maintainer.

When the release notes are ready, promote the release to the latest release with [`gh release edit`](https://cli.github.com/manual/gh_release_edit).

```bash
gh release edit v$VERSION --prerelease=false --latest
```

## 6. Update the Homebrew formula

Run this after promoting the release.

```bash
./scripts/update-homebrew-formula.sh $VERSION "<git user.name>" "<git user.email>"
```

This opens a PR on soracom/homebrew-soracom-cli that updates the version and the SHA256 checksums.

The script that updates the formula does not fail when downloading an asset fails (e.g. with 404), and opens the PR with wrong checksums. Before merging, make sure the checksums in the PR match those of the published assets.

```bash
gh api repos/soracom/soracom-cli/releases/tags/v$VERSION \
  -q '.assets[] | select(.name | test("_(darwin_(amd64|arm64)|linux_(amd64|arm64|386|arm))$")) | "\(.name) \(.digest)"'
```

After merging, run `brew update && brew upgrade soracom-cli && soracom version` to confirm that the new version is installed.

## 7. Publish the AWS Lambda Layers

Run this after promoting the release.

```bash
./scripts/build-lambda-layer.sh $VERSION
./scripts/release-lambda-layer.sh $VERSION <AWS profile name>
```

`build-lambda-layer.sh` downloads the binaries from the GitHub release and creates the layer zip files. `release-lambda-layer.sh` publishes two layers, `soracom-cli-<version>` (x86_64) and `soracom-cli-<version>-arm64`, to every region enabled in the AWS account (except ap-east-1) and grants everyone permission to use them. If you omit the AWS profile name, a profile for testing is used, so always specify the production profile.

> [!WARNING]
> The layer ARNs in the README assume version `:1`. Do not rerun the script if it fails partway. Rerunning it creates an additional `:2` in the regions where the layers were already published. The script cannot be limited to specific regions, so run `aws lambda publish-layer-version` and `aws lambda add-layer-version-permission` from the script manually for the remaining regions.

When it finishes, confirm that the layers can be retrieved with the ARNs in the README. Running the commands with credentials of an AWS account other than the one that published the layers also confirms that the layers are public.

```bash
aws lambda get-layer-version-by-arn --region ap-northeast-1 \
  --arn "arn:aws:lambda:ap-northeast-1:717257875195:layer:soracom-cli-${VERSION//./}:1"
aws lambda get-layer-version-by-arn --region ap-northeast-1 \
  --arn "arn:aws:lambda:ap-northeast-1:717257875195:layer:soracom-cli-${VERSION//./}-arm64:1"
```

## Snap

The Snap package (`soracom` on the Snap Store) is deprecated and is not updated on release.
